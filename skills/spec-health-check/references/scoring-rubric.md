# 评分细则（scoring-rubric）

健康度报告的评分规则：0-100 数值分 + Gate 红线判定。

## 分数模型

**分数完全由问题清单驱动**——每条问题按其归属维度扣分，保证"报告列了什么问题 → 分数就低多少"的自洽性，不允许凭印象调分。

### 公式

```
每维得分 = 100 − Σ(该维度 open 问题扣分)      # 下限 0
总分     = A×25% + B×30% + C×25% + D×20%     # 权重默认，可配置
等级     = A ≥90 | B 75-89 | C 60-74 | D <60
```

权重默认值及调整理由（B 一致性是 spec 可信度的核心，权重最高）：

| 维度 | 权重 | 说明 |
|:---|:---|:---|
| A 需求质量 | 25% | AC 可测试性是开发正确性的源头 |
| B 跨文档一致性 | 30% | 映射断裂 = 文档可信度崩塌，权重最高 |
| C 留痕真实性 | 25% | 与"实事求是"原则直接相关 |
| D 设计与计划质量 | 20% | 质量缺陷多数能由 B/C 维度的问题反映 |

### 扣分表

| 严重度 | 扣分 | 含义 |
|:---|:---|:---|
| CRITICAL | −20 | 结构缺失、大面积造假嫌疑、spec 无法作为回溯依据 |
| MAJOR | −10 | 覆盖缺口 >20%、明显不一致、真实性存疑 |
| MINOR | −3 | 个别覆盖缺口、表述矛盾、模板化记录 |
| NIT | −1 | 措辞、格式、可读性建议 |

> 扣分只作用于问题归属的维度；同一问题不得跨维重复扣分。已修复（✅）/接受（⏭️）的问题不扣分。

### 维度质量锚点（交叉校验用）

锚点不是第二套打分法，而是**漏报检测**：若某维得分按问题扣分算出很高，但文档表现明显落在低锚点档位，说明问题清单漏记，应补记问题而非直接调分。

| 锚点 | 分数参照 | A 需求质量 | B 跨文档一致性 |
|:---|:---|:---|:---|
| 优秀 | ≈95 | 所有 AC 可测试，范围边界清晰，无歧义 | AC↔测试↔任务映射无缺口，编号吻合 |
| 良好 | ≈80 | ≥80% AC 可测试，个别模糊措辞 | ≤20% AC 缺覆盖，主线完整 |
| 及格 | ≈60 | 多条 AC 不可测试，Out of Scope 缺失 | >20% 无覆盖，模块与任务脱节 |
| 不及格 | <60 | 无编号 AC，需求与验收脱节 | 文档间大面积脱节 |

| 锚点 | C 留痕真实性 | D 设计与计划质量 |
|:---|:---|:---|
| 优秀 ≈95 | CR 有真实发现（含 MINOR/NIT），记录含具体数据/路径/决策 | 架构图与文字一致，职责单一，任务粒度 15-30min |
| 良好 ≈80 | 留痕基本真实，个别记录偏模板化 | 个别任务粒度过大或依赖缺失 |
| 及格 ≈60 | CR 零问题 + 文档更新过薄 + 模板提示语复述 | 图与文字矛盾，模块职责混杂 |
| 不及格 <60 | 明确造假迹象（声称完成但空模板） | 无设计或任务清单不可执行 |

## 红线：Gate 条件集

Gate 仿 SonarQube Quality Gate——**由条件集判定而非单阈值**，任一条件命中即升级，防止总分稀释严重问题。

| Gate | 条件（任一命中） | 动作 |
|:---|:---|:---|
| 🟢 通过 | 无 open CRITICAL/MAJOR；总分 ≥85；每维 ≥75；open MINOR <3 | 可作回溯依据 |
| 🟡 关注 | 非 🔴 且（总分 70-84 / 任一维 60-74 / open MINOR ≥3） | 建议修复后交付 |
| 🔴 返修 | open CRITICAL>0 或 open MAJOR>0 或 总分<70 或 任一维<60 | **必须返工** |

判定逻辑伪码：

```
if 存在 open CRITICAL 或 open MAJOR → 🔴          # 一票否决，防稀释
elif 总分<70 或 任一维<60 → 🔴
elif 总分<85 或 任一维<75 或 open MINOR≥3 → 🟡
else → 🟢
```

## 部分填写 spec 的处理

开发中途的 spec（部分阶段未开始）：
- 只对已开始/已完成的阶段评分，未开始阶段标注"不适用"而非扣分
- 未开始阶段的空模板**不是**扣分项；但"已完成"阶段的空模板是 CRITICAL 问题
- 涉及未开始阶段的维度，分数按已开始部分折算，并在报告中注明计算口径

## 回归检查（报告已存在时）

重复检查是**回归**：核对上次问题清单的修复状态，再补新发现。

### 问题生命周期状态

| 状态 | 含义 | 分数影响 |
|:---|:---|:---|
| 🆕 | 本次新发现 | 扣分 |
| ✅ | 已修复（标注验证日期） | 不扣分（历史行的修复数 +1） |
| ⚠️ | 仍存在 | 继续扣分 |
| ⏭️ | 接受（有意保留，注明理由） | 不扣分（记入"接受"，不计入遗留） |

编号跨次永不复用：H-01 修复后打 ✅ 保留，不删除、不换号。

### 评分对比规则

- 每维与总分记录"上次 → 本次"，标注 ↑/↓/→
- 分数变化必须给出依据：修复了哪些问题（↑）、新增了哪些问题（↓）、或范围调整
- **严重度可跨次升级**：遗留问题 2 次以上无进展可上调一级（NIT→MINOR→MAJOR），扣分随之加重，提示修复闭环失效
- Gate 状态跨次对比：🟢→🔴 说明回归退化，报告结论需强调

### 检查历史表

每次检查追加一行，保留最近 5 次：

| # | 日期 | 模式 | Gate | 总分（等级） | 新增 | 修复 | 遗留 | 变化 |
|---|------|------|------|-------------|------|------|------|------|

- 修复数 = 本次从 ⚠️/🆕 转为 ✅ 的数量；遗留数 = 结束时仍为 ⚠️/🆕 的数量
- **连续两次修复数为 0** → 结论必须提示"检查闭环失效：问题未驱动修复"
- 历史表行数超过 5 时保留最近 5 次，更早的压缩（问题清单保留全部状态历史，编号不受影响）
