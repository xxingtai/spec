# Spec 健康度检查

## 核心原则

1. **双层检查** — 脚本管确定性的（结构、数字、一致性），模型管语义的（质量、真实性、歧义）
2. **数字交给脚本** — 所有统计（任务数、AC 数、测试用例数）以脚本 SUMMARY 块为准，**不要自己数数**
3. **只检查不修改** — 检查过程不改动被检查的 spec 文档；唯一写入的产物是 `health-report.md`
4. **重复检查即回归** — 报告已存在时，检查 = 拿上次问题清单核对修复状态 + 追加新发现，更新同一份报告
5. **实事求是** — 报告如实反映问题，包括"留痕真实性"层面的疑点

## 检查对象

符合以下结构的 spec 目录（由 spec-dev-workflow 的 init-spec.sh 生成，或其他来源的等价结构）：

```text
<spec-dir>/
  00-index.md          进度索引（阶段状态表）
  01-requirements.md   需求（含 AC-xx 验收标准）
  02-design.md         设计
  03-implementation-plan.md   实现计划（T-xx 任务）
  04-unit-test-plan.md        单元测试
  05-integration-test-plan.md 集成测试
  06-code-review-report.md    CR 报告
  07-docs-update-plan.md      文档更新
  08-commit.md         完成记录
```

## 执行流程

### 第一步：运行脚本层检查

跨平台（Python 3.7+，Windows/Linux/macOS 原生可跑）：

```bash
python <skill目录>/scripts/health-check.py <spec根目录> <名称> [--version <版本>]
```

Git Bash / WSL 环境亦可用等价的 bash 版（同一套输出与退出码）：

```bash
bash <skill目录>/scripts/health-check.sh <spec根目录> <名称> [--version <版本>]
```

示例：

```bash
python <skill目录>/scripts/health-check.py /home/deng/work/tonghuashun/spec v1.0
python <skill目录>/scripts/health-check.py ./spec v0.0 --version V1
```

从输出中获取：
- **结构检查结果**（文件缺失、空模板、占位符残留）
- **SUMMARY 块**（所有统计数据，作为模型层评审的数字依据）
- **一致性告警**（脚本层已判定的矛盾）
- **`has_report`**（决定走首次还是回归分支）

### 第二步：模型层评审

**先依据 `has_report` 选择评审范围：**

- `has_report=0` → **首次检查**：全量四维评审（下方"四维评审框架"），报告作为 baseline
- `has_report=1` → **回归检查**：按"回归阅读策略"控制范围，不重读全部文档

#### 四维评审框架（首次全量用）

逐个阅读 spec 文档，先产出问题清单（每条按严重度 + 归属维度），分数在第三步由问题扣分驱动（锚点与细则见 `references/scoring-rubric.md`）。

##### 维度 A：需求质量（01-requirements.md）

- **AC 可测试性**：每条 AC 是否包含明确的"输入/操作 → 预期结果"，能否直接转化为测试用例？是否有"快速"、"大量"、"友好"这类不可验证的表述？
- **范围边界**：In Scope / Out of Scope 是否清晰？有无 scope creep 迹象？
- **歧义检测**：同一概念在不同段落是否有不同称谓？约束是否前后一致？
- **非功能需求**：性能/安全/兼容性是否按项目类型取舍，还是留着模板示例没改？

##### 维度 B：跨文档一致性（核心维度）

- **AC ↔ 04**：逐条 AC 检查是否有对应测试用例（构建 AC-TC 映射表，标出无覆盖的 AC）
- **AC ↔ 03**：每条 AC 是否有任务实现它（标出无任务支撑的 AC）
- **02 ↔ 03**：03 的任务分组是否对应 02 的模块清单？有无 02 设计了但 03 没拆解的模块？
- **03 ↔ 08**：08 的 commit 记录引用的任务编号是否存在于 03？
- **00-index ↔ 实际**：声称"已完成"的阶段，对应文档内容是否支撑该结论？

##### 维度 C：留痕真实性（对应"实事求是"原则）

- **CR 全绿可疑**：06 报告零问题（脚本会告警）时，抽查代码/文档判断审查是否真实发生过
- **文档更新流于形式**：07 是否只有模板框架没有实际更新内容（结合 doc_07_bytes 判断）
- **模板填空 vs 真实记录**：文档内容是否只是复述模板提示语，还是记录了实际发生的决策和数据（真实文档通常包含具体数字、具体文件路径、踩坑记录）

##### 维度 D：设计与计划质量

- **02 架构图与文字一致**：Mermaid 图中的模块/流向是否与文字描述吻合
- **模块职责**：02 模块清单是否职责单一、接口清晰
- **03 任务粒度**：任务是否在 15-30 分钟粒度？依赖关系是否明确？

#### 回归阅读策略（回归检查用，控制上下文）

回归检查的目标是验证"上次的问题是否修复 + 有无新增问题"，不需要每次重读全部文档：

1. 旧报告的检查历史与问题清单即 baseline（必读，几十行）
2. 将脚本 SUMMARY 的关键数字（AC 数 / 任务数 / 测试数 / CR 数 / 07 字节数）与旧报告记录对比——**数字变化 → 对应文件必然被改动，详读该文件**
3. 对每项"仍存在"问题：只读其对应文件的相关章节核对修复状态
4. 随机抽 1-2 个文件做质量抽检，确认无系统性退化
5. spec 若在 git 仓库，用 git diff/log 辅助判断改动范围

### 第三步：评分与红线判定

评审完成后按以下步骤计算分数与 Gate 状态：

1. 将每条问题按其归属维度归类
2. **每维得分 = 100 − Σ(该维度 open 问题扣分)**——分数完全由问题清单驱动，保证分数与问题自洽
3. **加权总分**：A 需求 25% / B 一致性 30% / C 真实性 25% / D 设计 20%（权重可配置，见 rubric）
4. 依下方条件集判定 Gate：🟢 / 🟡 / 🔴
5. **交叉校验**：某维得分与 rubric 锚点档位明显脱节时，检查是否漏记问题（分数必须由问题驱动，不允许凭感觉调分）

### 第四步：生成或更新健康度报告

报告是 spec 目录下的**单份** `health-report.md`（不占用 00-08 编号），重复检查更新同一份，不另建文件。**Gate=🔴 时报告结论必须给出按严重度排序的返修指引，并提示修复后回归检查验证转绿。**

**回归检查的更新流程**：
1. 读取现有 `health-report.md`，提取遗留问题（状态为 ⚠️ / 🆕 的项）
2. 逐项核对修复状态并更新：`✅ 已修复`（本次验证）/ `⚠️ 仍存在` / `⏭️ 接受`（有意保留）
3. 按回归阅读策略重评审，追加本次新发现（编号从现有最大号 +1）
4. 检查历史表追加一行；各维度与总分记录"上次 → 本次"；Gate 与总分标注变化（↑/↓/→）
5. 若上次遗留问题全部未修复（修复数为 0），在结论中明确提示"**检查闭环失效：问题未驱动修复**"

**问题编号与生命周期**：
- 编号跨次永不复用：H-01 修复后标记 ✅，不删除——历史表的"修复/遗留"数字才能对上账
- 新问题从现有最大编号 +1 追加
- 状态四种：`🆕 新增` / `✅ 已修复（日期）` / `⚠️ 仍存在` / `⏭️ 接受`
- 严重度可跨次调整：遗留问题长期未修可升级（如 NIT 拖多次 → MINOR，提示修复闭环失效）

**报告模板（v3）**：

```markdown
# {spec 名称} 健康度报告

> 最近更新：{YYYY-MM-DD}｜最近模式：{首次/回归}
> Gate：{🟢 通过 / 🟡 关注 / 🔴 返修}（总分 {分数}，等级 {A-D}）

## 检查历史

| # | 日期 | 模式 | Gate | 总分（等级） | 新增 | 修复 | 遗留 | 变化 |
|---|------|------|------|-------------|------|------|------|------|
| 1 | {YYYY-MM-DD} | 首次 | 🟢 | 91.5（A） | 5 | — | 5 | — |

## 当前状态

- 总分：{分数}（等级 {A-D}；上次 {分数}，{↑/↓/→}）
- Gate：{🟢/🟡/🔴}（Gate 非绿时列明命中的触发条件）

## 分维度评分

| 维度 | 权重 | 上次 | 本次 | 主要依据（锚点 + 该维扣分问题） |
|:---|:---|:---|:---|:---|
| A 需求质量 | 25% | — | {分数} | 一句话 |
| B 跨文档一致性 | 30% | — | {分数} | 一句话 |
| C 留痕真实性 | 25% | — | {分数} | 一句话 |
| D 设计与计划质量 | 20% | — | {分数} | 一句话 |

## 结构检查结果（脚本层）

- 文件完整性 / 占位符 / 统计数字（从 SUMMARY 块摘录）

## 问题清单（按严重度排序，含扣分与生命周期状态）

| 编号 | 严重度（扣分） | 维度 | 位置 | 问题描述 | 修复建议 | 状态 |
|:---|:---|:---|:---|:---|:---|:---|
| H-01 | MINOR（−3） | C | 文件+章节 | 具体问题 | 具体建议 | 🆕 / ✅（日期）/ ⚠️ / ⏭️ |

## AC 覆盖映射（维度 B 详情）

| AC 编号 | 测试覆盖（04） | 任务覆盖（03） | 状态 |
|:---|:---|:---|:---|
| AC-01 | 用例名/无 | T01/无 | ✅/⚠️ |

## 结论与建议

- 总体评价；回归检查时说明本次修复 / 新增 / 遗留各多少
- Gate=🔴：给出按严重度排序的返修指引；Gate=🟡：建议修复项；Gate=🟢：可作回溯依据
```

### 评分标准（分数模型）

分数完全由问题清单驱动，保证分数与报告列出的问题自洽：

- 每维得分 = 100 − Σ(该维度 open 问题扣分)；总分 = 每维加权（A 25% / B 30% / C 25% / D 20%）
- 等级映射：A ≥90 / B 75-89 / C 60-74 / D <60

| 严重度 | CRITICAL | MAJOR | MINOR | NIT |
|:---|:---|:---|:---|:---|
| 扣分 | −20 | −10 | −3 | −1 |

### 红线（Gate 条件集）

Gate 是条件集而非单阈值（仿 SonarQube Quality Gate），**任一条件命中即升级**，防总分稀释严重问题：

| Gate | 条件（任一命中） | 动作 |
|:---|:---|:---|
| 🟢 通过 | 无 open CRITICAL/MAJOR；总分 ≥85；每维 ≥75；open MINOR <3 | 可作回溯依据 |
| 🟡 关注 | 非 🔴 且（总分 70-84 或任一维 60-74 或 open MINOR ≥3） | 建议修复后交付 |
| 🔴 返修 | open CRITICAL>0 或 open MAJOR>0 或 总分<70 或 任一维<60 | **必须返工** |

**Gate=🔴 动作协议**：
1. 对话回复开头给醒目标记（Gate 状态 + 当前总分）
2. 输出返修指引：按"必须先修"排序（CRITICAL/MAJOR 优先，其次最低分维度的 MINOR），每项带定位与改法
3. 明确提示"修复后重跑健康检查（回归模式）验证转绿"

严重度沿用 06-code-review-report.md 的定义：CRITICAL / MAJOR（阻塞）/ MINOR / NIT（不阻塞）。完整细则见 `references/scoring-rubric.md`。

## 边界与约束

- **只读 spec 文档**（health-report.md 除外）；需要看代码来判断 CR 真实性时，只读不写
- **不重复数数**：所有计数以 SUMMARY 块为准，正文只做定性判断
- **报告落盘后向用户汇报摘要**：本次模式（首次/回归）、Gate 状态 + 总分及变化、修复/新增/遗留数、Top 问题、下一步建议；Gate=🔴 时按动作协议爆红提示
- 部分填写的 spec（开发中途）也可以检查，此时重点检查已完成阶段的可信度，未开始阶段标注"不适用"而非扣分
