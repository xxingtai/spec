# 需求阐述指南

## 需求澄清框架

### 1. 功能目标（WHY）

- 这个功能要解决什么问题？
- 当前的痛点是什么？
- 做完后用户的工作方式会有什么变化？

### 2. 用户场景（WHO + WHEN）

- 谁会使用这个功能？
- 在什么场景下触发？
- 使用频率如何？

### 3. 功能范围（WHAT）

**做什么（In Scope）：**
- 核心功能点逐条列出

**不做什么（Out of Scope）：**
- 明确排除的功能，防止 scope creep

### 4. 验收标准（HOW）

每条验收标准必须满足 SMART 原则：

- **Specific**：具体明确，不模糊
- **Measurable**：可量化或可验证
- **Achievable**：技术上可行
- **Relevant**：与功能目标相关
- **Time-bound**：可在迭代内完成

### 5. 非功能需求

- 性能：响应时间、并发量
- 安全：认证、授权、数据保护
- 兼容性：浏览器、操作系统、设备
- 可用性：无障碍访问

### 6. 依赖关系

- 依赖哪些现有模块？
- 需要哪些外部 API 或服务？
- 是否需要数据库变更？

## 需求文档检查清单

- [ ] 每条验收标准都是可测试的
- [ ] 功能范围边界清晰
- [ ] 非功能需求已明确
- [ ] 依赖关系已识别
- [ ] 无歧义表述

## 常见问题

### 需求太模糊怎么办？

用"5个为什么"法追问：
1. 用户为什么需要这个功能？
2. 当前怎么解决的？
3. 新方案比旧方案好在哪？
4. 最小可用版本是什么？
5. 做完后验证什么指标？

### 验收标准写不出来怎么办？

先写"成功场景"和"失败场景"，再转化为具体标准：
- 成功场景：用户输入正确密码 → 登录成功 → 跳转首页
- 失败场景：用户输入错误密码 → 提示"密码错误" → 3次后锁定
