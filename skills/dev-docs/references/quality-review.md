# 独立评估清单：文档语义正确性复核（v1.5.2）

> 时机：机器门禁（`check --strict`）**全绿之后**、交付之前。
> 执行者：**另一** agent 或人（不与填写者同一个上下文，避免"自查"盲区）。
> 事实来源：**源码本身**（不是 inventory，更不是被评估的文档）。
> 为什么必须有：机器门禁只覆盖结构、覆盖、行号位置、卡片填尽——
> **语义正确性**（事实与源码是否一致、有无编造 / 张冠李戴 / 把死代码当现行约定）机器无法判定。
> 实测教训：一次端到端交付中，机器门禁全绿，独立评估仍发现 **4 处 P0**（详见 anti-patterns 13-16）。

## 1. 评估方式

> 起手先跑 `dev_docs.py audit --write` 生成**工作底稿**（v1.5.4）：机器已核行性质、
> 卡片签名与盘点一致性、零引用断言、地图引用与重词，并排给出"文档原句 vs 源码原文"。
> 底稿只替代**机械核对**——底稿下的语义判断（叙述与源码说的是一回事吗）仍须逐条人工完成。

| 项 | 要求 |
|:---|:---|
| 抽样下限 | **≥25 处** file:line 引用、**≥15 张**卡片、3 页叙事章节全覆盖 |
| 抽样分布 | 覆盖所有包/模块；C++ 与 Python（及项目实际语言）都要有；含机器区与叙事区 |
| 核对方式 | 逐条打开被引用的源码位置，确认**该行内容与文档叙述一致**（audit 底稿已并排给出，逐条判语义即可） |
| 纪律 | 不因"看起来专业"给好评；只报能从源码验证的问题；引用行号必须在源码里核对而非复述文档 |

## 2. 核查清单（逐项过）

1. **file:line 准确性**：文件存在？行号指向的内容与叙述一致？是否指向空行 / 注释 / 字符串内的"注释掉的代码"？
2. **卡片语义**：用途/参数/返回/错误与源码行为一致？有无**编造**（描述的功能不存在）、**张冠李戴**（A 的说明安给 B）？
3. **叙事章节**：架构边界图 / 组件关系图 / 运行时场景的连线与步骤是否与真实拓扑一致（方向、缺环节、编造依赖）？
4. **可执行性**：`usage` 里的安装/启动/排查命令能否照做？配置默认值与源码一致？
5. **完整性与契约**：接口/话题/服务有无漏？**跨模块契约两侧口径是否一致**（同一消息码/字段名/单位，两侧定义是否吻合）？
6. **一致性**：同一事实在不同页面的说法是否一致？文档间链接有效？

## 3. 输出格式

```
总体结论（能不能交付；最大风险一句话）

P0（错误/编造，必须修）   —— 文档位置（文件:行）→ 源码事实（文件:行）→ 问题描述 → 修复建议
P1（重要遗漏/不准确）     —— 同上
P2（改进项）             —— 同上

抽样统计表：引用 N 处（对/错）、卡片 N 张（对/误）、叙事 N 页
```

## 4. 交付判定

| 级别 | 处置 |
|:---|:---|
| P0 | **修完才交付**；修完建议对修改点做一次回归抽核 |
| P1 | 修完交付，或在交付说明中显式列出 |
| P2 | 记录，可留待后续 |

> 修完后跑一次 `check --strict`（结构门禁仍须全绿），并把评估结论写进交付说明。

## 5. 高发错误模式（评估时优先盯）

1. **语义地图 / LLM 自由文本**被当事实渲染进机器区（编造"本地数据库"之类）
2. **注释 / 字符串里的代码**被当成真实行为（三引号块、`/* */` 注释掉的分支）
3. **调用点注释**被当成**定义处**的功能说明
4. **零引用的常量/函数**被写成现行约定（死代码）
5. **跨模块契约两侧口径不一致**（同一码值两侧含义不同）被描述为"约定一致"
6. **构建声明与实物不符**（CMakeLists 声明了 msg/srv 但文件缺失）——文档照抄会让读者编译失败
